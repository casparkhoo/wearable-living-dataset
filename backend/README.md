# Backend

The backend is the data and control plane for the wearable system.

It owns:

- subscribing to MQTT packets from the Android application
- writing untouched packets to MySQL `raw_packets`
- normalizing packets into canonical `stream_samples`
- serving live and historical data to the desktop viewer
- query-time post-processing and CSV/model-ready export
- owning experiment, device-recording and activity-label control over REST
- publishing low-rate control/status events on MQTT `status/#`
- optionally coordinating replaceable ML inference workers

It does not require ML inference to be running. The wearable dataset is valid on its own.
Post-processing must not alter `raw_packets` or `stream_samples`. Windows,
resampled values, selected features, CSV files and model inputs are generated on
demand and returned with a reproducibility manifest rather than stored as evidence.

## Layout

- `schema.sql` creates the single MySQL living-dataset schema.
- `migrations/` contains additive upgrades and historical migration records.
- `setup_database.ps1` reads the local `.env`, applies `schema.sql`, then applies
  the current idempotent upgrades. It deliberately skips historical one-time files
  whose changes are already included in `schema.sql`.

From the repository root, initialize or upgrade the local database with:

```powershell
.\backend\setup_database.ps1
```
- `.env.example` documents runtime configuration.
- `src/` is reserved for the backend service implementation.
- `src/preprocessing.rs` is a boundary for later preprocessing logic.

## Intended Flow

```text
Android -> MQTT broker -> backend ingester -> MySQL wearable_living_dataset
       \-> REST control -> backend --------/
                                      |
                                      -> live backend API/WebSocket
                                      |
                                      -> optional ML inference workers
```

## Database Boundary

The living dataset is one MySQL schema with separate tables for separate roles:

- `devices`
- `experiments`
- `sessions` (device recordings)
- `annotations` (activity labels)
- `measurement_configs`
- `raw_packets`
- `stream_samples`

Native canonical samples stay in `stream_samples`. A window is a derived selection
over those samples. It is generated by the post-processing engine and exported with
its source range and parameters rather than inserted back into the database as if it
were new evidence. PaPaGei and other models consume that query result; no core table
or acquisition route is named after a model.
